# Як ми побудували MCP-сервер на 70 інструментів для юридичного AI — уроки архітектури

*Один endpoint. Три сервіси. Потрійний транспорт. Ось що потрібно, щоб побудувати продакшн MCP-сервер, який дійсно масштабується.*

---

## Проблема: юридичний AI потребує більше, ніж один API-виклик

Коли юрист запитує "Негаторний чи віндикаційний позов при самовільному захопленні земельної ділянки?" — відповідь вимагає:

- Пошуку 200+ судових рішень за різними формулюваннями
- Отримання повного тексту статті 391 ЦК та статті 212 ЗК
- Порівняння практики "за" та "проти"
- Перевірки, які прецеденти ще чинні
- Синтезу всього у стратегічну рекомендацію

Це не один виклик LLM. Це оркестрований пайплайн з 5-7 tool calls, кожен з яких звертається до різних джерел даних, кожен зі своїм профілем витрат та латентності.

Нам потрібна була система, де AI-агент може виявляти, обирати та виконувати десятки спеціалізованих юридичних інструментів в одній розмові. MCP (Model Context Protocol) дав нам фреймворк. Продакшн навчив решти.

## Архітектура: 70 інструментів, три сервіси, один шлюз

### Розподіл по сервісах

Наша платформа працює на трьох незалежних MCP-серверах, кожен відповідає за свій домен:

| Сервіс | Інструменти | Домен |
|--------|-------------|-------|
| **mcp_backend** | 50 | Судові рішення, законодавство, семантичний пошук, сховище документів, due diligence |
| **mcp_rada** | 4 | Парламентські дані — законопроєкти, депутати, голосування, тексти законів |
| **mcp_openreyestr** | 16 | Державний реєстр — юридичні особи, бенефіціари, боржники, виконавчі провадження |
| **Всього** | **70** | |

Кожен сервіс — самостійний Node.js/TypeScript-додаток зі своїм PostgreSQL, Redis, та (для бекенду) векторною базою Qdrant.

### Уніфікований шлюз

У продакшені клієнтам не потрібно знати про три сервіси. Одна змінна середовища — `ENABLE_UNIFIED_GATEWAY=true` — перетворює бекенд на точку агрегації:

```
Клієнт → POST /api/tools/rada_search_parliament_bills
        → Шлюз перевіряє ToolRegistry
        → Route: { service: 'rada', local: false }
        → ServiceProxy → POST rada-service:3001/api/tools/search_parliament_bills
        → Відповідь повертається клієнту
```

`ToolRegistry` підтримує дві структури даних:

```typescript
private routes: Map<string, ToolRoute>;        // усі маршрути (локальні + віддалені)
private handlerMap: Map<string, BaseToolHandler>; // обробники локальних інструментів
```

Локальні інструменти виконуються в процесі. Віддалені проксуються через HTTP із заголовком `X-Parent-Request-ID` для розподіленого трасування. Визначення віддалених інструментів завантажуються ліниво при першому `GET /api/tools` та кешуються на весь час життя процесу.

Конвенція префіксів робить маршрутизацію однозначною: `rada_*` йде до RADA, `openreyestr_*` до OpenReyestr, все інше — локальне.

## Потрійний транспорт: один сервер, три протоколи

Кожен MCP-сервер підтримує три способи підключення. Це не дизайнерський вибір — це вимога виживання. Різні клієнти говорять різними протоколами.

### Транспорт 1: stdio (MCP Native)

```typescript
const transport = new StdioServerTransport();
await this.server.connect(transport);
```

Чистий JSON-RPC через stdin/stdout. Це те, що використовують Claude Desktop та інші MCP-нативні клієнти. Без HTTP, без портів, без автентифікації — клієнт запускає наш сервер як підпроцес.

**Коли важливо:** Локальна розробка, інтеграція з Claude Desktop, тестування MCP CLI. Нульовий оверхед, миттєве виявлення інструментів.

### Транспорт 2: HTTP REST API

```
POST /api/tools/:toolName       → виконання інструменту
POST /api/tools/:toolName/stream → SSE стрімінг
POST /api/tools/batch            → паралельне виконання
GET  /api/tools                  → список усіх інструментів (+ віддалені через шлюз)
```

Стандартний REST із Bearer token автентифікацією. Це те, що використовує наш веб-фронтенд. Заголовок `Accept: text/event-stream` на звичайному endpoint перемикає відповідь на SSE — окремий URL не потрібен.

**Коли важливо:** Веб-додатки, API-інтеграції, все що говорить HTTP. Batch endpoint критичний для агентного циклу — коли план AI каже "запусти ці 3 пошуки паралельно", ми робимо `Promise.all()`.

### Транспорт 3: SSE (MCP-over-SSE)

Ми фактично запускаємо два варіанти SSE:

**Варіант A (`/sse`)** — протокол інтеграції з ChatGPT/OpenAI. Один HTTP-запит на JSON-RPC повідомлення, повне OAuth discovery (`/.well-known/oauth-authorization-server`), keepalive ping кожні 30с.

**Варіант B (`/v1/sse`)** — стандартний MCP SSE-транспорт з SDK. Створює новий екземпляр MCP `Server` на кожне з'єднання з повним життєвим циклом сесії. Для віддалених підключень Claude Desktop та інших стандартних MCP-клієнтів.

**Коли важливо:** Віддалені MCP-клієнти, розподілені архітектури, з'єднання через реверс-проксі, що потребують довготривалого стрімінгу.

## Патерн BaseToolHandler

Кожен доменний інструмент розширює один абстрактний клас:

```typescript
export abstract class BaseToolHandler {
  abstract getToolDefinitions(): ToolDefinition[];
  abstract executeTool(name: string, args: any): Promise<ToolResult | null>;

  protected wrapResponse(data: any): ToolResult { ... }
  protected wrapError(message: string): ToolResult { ... }
}
```

Це дає нам:

- **Стандартизовану обробку помилок.** `wrapError()` ставить `isError: true` у MCP-відповіді. HTTP-шар повертає `200 OK` незалежно (конвенція MCP) — помилки in-band, а не HTTP статус-коди.
- **Консистентну реєстрацію.** `toolRegistry.registerHandler(handler)` ітерує `handler.getToolDefinitions()` і автоматично заповнює handler map. Додати новий доменний інструмент — один рядок у конструкторі.
- **Опціональний стрімінг.** `executeToolStream?()` — необов'язковий. Реєстр перевіряє `supportsStreaming(name)` перед маршрутизацією на стрімінговий шлях.

13 класів-обробників покривають весь домен: `CourtDecisionTools`, `ProceduralTools`, `LegislationTools`, `VaultTools`, `DocumentAnalysisTools`, `DueDiligenceTools`, `BusinessRegistryTools`, `ECHRPracticeTools` та інші.

## Потік виклику інструменту: 11 кроків від запиту до відповіді

Ось що відбувається, коли приходить `POST /api/tools/search_legal_precedents`:

1. **`dualAuth` middleware** — валідує Bearer token як JWT (веб-користувачі) або API-ключ (програмні клієнти)
2. **Перевірка балансу** — верифікує достатність кредитів на акаунті; повертає `402` якщо ні
3. **Розрахунок кредитів** — оцінює кредити для конкретного інструменту
4. **Запис трекінгу витрат** — вставляє `pending` рядок у таблицю `cost_tracking` з метаданими запиту
5. **Оцінка вартості** — логує розрахункову вартість перед виконанням
6. **Маршрутизація шлюзу** — перевіряє, локальний чи віддалений інструмент; проксує якщо віддалений
7. **Локальне виконання** — запускається в контексті `AsyncLocalStorage`, щоб усі подальші виклики OpenAI автоматично прив'язували використання токенів до цього request ID
8. **Диспатч обробника** — `toolRegistry.executeTool()` → `handler.executeTool()` → доменна логіка
9. **Завершення трекінгу витрат** — записує фактичне використання токенів, час виконання, статус
10. **Списання кредитів** — стягується після успішного виконання, не до
11. **Відповідь** — включає результат, розбивку витрат та request ID для трасування

Патерн `AsyncLocalStorage` заслуговує окремої уваги. Кожен tool call, який внутрішньо використовує OpenAI embeddings або completions, повинен відстежувати використання токенів. Замість того, щоб передавати `requestId` через 6 рівнів викликів, ми обгортаємо виконання в `requestContext.run()`. Будь-який виклик OpenAI де завгодно в дереві викликів автоматично знаходить поточний контекст запиту та записує свої токени.

## Патерни, які нас врятували

### Підказки вартості в описах інструментів

Кожен опис інструменту містить розрахункову вартість:

```
💰 Приблизна вартість: $0.01-$0.04 USD
Вартість залежить від глибини аналізу...
```

Це пропагується до LLM-клієнтів. Коли AI-агент планує, які інструменти викликати, він може враховувати вартість до виконання. Класифікаційний виклик `quick` коштує $0.001. Глибокий юридичний аналіз — $0.10. AI це бачить і адаптується.

### Budget-Aware вибір моделі для кожного інструменту

Багато інструментів мають параметр `reasoning_budget`:

```typescript
reasoning_budget: {
  type: 'string',
  enum: ['quick', 'standard', 'deep'],
  default: 'standard'
}
```

Це передається в `ModelSelector`, який маппить на різні моделі OpenAI: `quick → gpt-5-nano`, `standard → gpt-5-mini`, `deep → gpt-5.1`. Один і той самий інструмент може працювати дешево або дорого залежно від запиту.

### Ізоляція Vault-інструментів по користувачах

Vault-інструменти (сховище документів) потребують скоупінгу по користувачах, але MCP-схема не повинна показувати параметри автентифікації. Ми інжектимо user ID на рівні транспорту:

```typescript
const VAULT_TOOLS = new Set(['store_document', 'get_document', 'list_documents', 'semantic_search']);
const toolArgs = VAULT_TOOLS.has(toolName) ? { ...args, userId } : args;
```

Обробник інструменту отримує `userId` так, ніби клієнт його передав. Чистий розподіл між автентифікацією та бізнес-логікою.

### Нормалізація маршрутів для метрик

З 70 інструментами та UUID в URL кардинальність Prometheus вибухає швидко. Наш `MetricsService` нормалізує маршрути перед записом:

- `/api/tools/search_legal_precedents` → `/api/tools/:toolName`
- `/api/documents/a1b2c3d4-...` → `/api/documents/:id`

Без цього кожен унікальний виклик інструменту створює нову time series. З цим — усього ~20 міток маршрутів.

## Що б ми зробили інакше

**Почали б зі шлюзу з першого дня.** Ми спочатку побудували три окремі сервіси, потім прикрутили уніфікований шлюз. Конвенція префіксів (`rada_*`, `openreyestr_*`) працює, але виглядає як латка. Якби починали заново — спроєктували б простір імен інструментів наперед.

**Валідація схеми на рівні реєстру.** Зараз кожен обробник валідує свій вхід самостійно. Централізований крок валідації в `executeTool()` за JSON Schema з `getToolDefinitions()` ловив би некоректні запити до того, як вони досягнуть коду обробника.

**Стрімінг для всіх інструментів.** Ми зробили стрімінг опціональним. На практиці кожен інструмент, що працює довше 2 секунд, повинен стрімити події прогресу. Користувач, який дивиться на спінер 10 секунд під час глибокого аналізу — це поганий UX. Ми зараз це ретрофітимо.

## Цифри

- **70 інструментів** через 3 сервіси
- **13 класів-обробників** тільки в бекенді
- **3 транспортні протоколи** на кожен сервіс
- **11-кроковий пайплайн виконання** з трекінгом витрат на кожному етапі
- **5 191 стаття законодавства** попередньо завантажена та доступна для пошуку
- **16 українських державних реєстрів** доступні в реальному часі
- Середня латентність tool call: **200мс** (кеш) до **8с** (глибокий аналіз з ембедінгами)

Протокол MCP дав нам стандартний спосіб описувати та виявляти інструменти. Інженерний виклик був у всьому іншому: трекінг витрат, управління кредитами, агрегація багатьох сервісів, ізоляція користувачів і забезпечення спостережуваності всього цього.

Кількість інструментів буде рости. Архітектурі все одно.
