# Чому ми відмовились від Round-Robin між OpenAI та Anthropic — і що використовуємо замість

*Розробка юридичної AI-платформи навчила нас: мультипровайдерна LLM-маршрутизація чудово виглядає на архітектурних діаграмах, але ламається у продакшені.*

---

## Ідея, яка мала ідеальний сенс

Коли ми почали будувати LEX AI — платформу для аналізу мільйонів українських судових рішень — ми зробили те, що робить кожна AI-first команда: інтегрували кілька LLM-провайдерів.

OpenAI для структурованого виводу. Anthropic для глибокого юридичного аналізу. Round-robin між ними для стійкості та оптимізації витрат.

На папері це виглядало елегантно. У продакшені це був кошмар.

## Що пішло не так

### 1. Фрагментація форматів відповідей

Наш агентний пайплайн виконує до 5 ітерацій tool-calling на кожен запит користувача. Кожна ітерація очікує нормалізовану відповідь: `tool_calls`, `finish_reason`, структурований JSON.

OpenAI та Anthropic повертають це по-різному. Ми побудували шар нормалізації. Він обробляв 90% випадків. Решта 10% — порожні відповіді, неповний JSON, неочікувані stop reasons — спричиняли тихі збої глибоко в циклі.

Один баг ми шукали 3 дні: Anthropic іноді повертав валідну відповідь зі `stop_reason: "end_turn"` замість `"tool_use"`, яку наш нормалізатор пропускав далі, але наступна ітерація сприймала як фінальну відповідь. Користувач отримував напівготовий аналіз без жодної індикації, що щось пішло не так.

### 2. Один промпт — дві різні поведінки

Юридичний AI живе і вмирає від точності промптів. Наш системний промпт інструктує модель діяти як український юридичний асистент, класифікувати наміри, обирати інструменти та відповідати в структурованому форматі.

Claude точніше виконував інструкції українською мовою. GPT генерував чистіші JSON tool calls. Коли модель змінювалась на кожній ітерації агентного циклу, якість результату ставала підкиданням монети.

Крок класифікації на GPT видавав "civil_property". Той самий запит на Claude — "civil_law_property_dispute". Наш downstream tool router очікував точні збіги.

### 3. Дебагінг перетворився на археологію

Коли користувач повідомляв про поганий результат, ми дивились на трейс:

- Крок 1: OpenAI (класифікував намір)
- Крок 2: Anthropic (згенерував план пошуку)
- Крок 3: OpenAI (виконав інструменти)
- Крок 4: Anthropic (синтезував відповідь)

Який крок зламався? Модель чи нормалізація? Чи можемо відтворити? Ні — наступний запуск маршрутизує інакше.

Ми витрачали більше часу на дебагінг шару маршрутизації, ніж на покращення самого юридичного аналізу.

### 4. "Оптимізація" витрат, якої не було

Round-robin мав балансувати витрати. Натомість:

- Ціни Anthropic на глибокі аналітичні запити були в 2-3 рази вищими за еквівалент OpenAI
- Але Anthropic був дешевшим на коротких запитах класифікації
- Round-robin повністю це ігнорував — він просто чергував

Ми платили преміум-ціну за завдання, які не потребували преміум-моделей, і використовували бюджетні моделі для завдань, яким потрібні були потужні.

### 5. Два набори всього

Кожен провайдер має своє:
- Rate limits (різні пороги, різні заголовки)
- Retry-стратегії (різні рекомендації backoff)
- Формати помилок (різні HTTP-коди для однієї проблеми)
- Оновлення SDK (breaking changes за різними графіками)

Наш "уніфікований" retry-шар насправді був двома retry-шарами у одному тренчкоті.

## Що ми робимо зараз

Ми захардкодили OpenAI як єдиного провайдера та інвестували зекономлену складність у **budget-aware вибір моделі в межах одного провайдера**:

```
quick    → gpt-5-nano    (класифікація наміру, маршрутизація)
standard → gpt-5-mini    (виконання інструментів, сумаризація)
deep     → gpt-5.1       (юридичний аналіз, витяг патернів)
```

Один формат API. Одна обробка помилок. Одна retry-логіка. Передбачувані витрати. Відтворювані результати.

Тег `@deprecated` на нашому методі `getNextProvider()` — найкращий рядок коду, який ми написали за рік.

## Як правильно використовувати кілька провайдерів (якщо дуже треба)

Ось що ми рекомендуємо після навчання на власних помилках:

**Task routing, а не round-robin.** Призначте кожному провайдеру конкретні типи завдань назавжди. Класифікація завжди йде на Провайдера А. Глибокий аналіз завжди на Провайдера Б. Ніколи не чергуйте всередині одного пайплайну.

**Fallback, а не чергування.** Провайдер Б активується лише коли Провайдер А повертає 429 або 500. Це стійкість. Round-robin — це хаос.

**Мультиключ одного провайдера.** Якщо rate limits — ваше вузьке місце, використовуйте кілька API-ключів від одного провайдера з ротацією. Той самий формат, та сама поведінка, вищий throughput.

**A/B тестування офлайн.** Порівнюйте провайдерів в окремому evaluation-пайплайні з фіксованими тест-кейсами. Ніколи не проводьте A/B тести у продакшн-потоках з реальними користувачами.

## Чому AWS Bedrock змінює правила гри

Якби ми починали сьогодні, ми б повністю пропустили прямі API-ключі та обрали AWS Bedrock. Ось чому:

**Один endpoint — усі моделі.** Claude, Llama, Mistral, Titan — все доступне через один AWS SDK. Перемикання моделей означає зміну рядка `modelId`, а не заміну SDK.

**Жодних API-ключів у вашому середовищі.** Bedrock використовує IAM roles. Ваш EC2-інстанс отримує дозволи через свою роль — жодного `OPENAI_API_KEY` у `.env`-файлі, який хтось випадково закомітить.

**Ваші дані залишаються у вашому регіоні.** Для legal tech це критично. Коли ви викликаєте API OpenAI, ваші дані летять на їхню інфраструктуру. З Bedrock у `eu-central-1` дані ніколи не залишають ваш AWS-акаунт. Для платформи, що обробляє конфіденційні судові документи та дані клієнтів, це не nice-to-have — це вимога compliance.

**Єдиний білінг та моніторинг.** Один рахунок AWS замість окремих інвойсів від OpenAI та Anthropic. CloudWatch-метрики з коробки замість написання власного cost tracker.

**Provisioned throughput.** Замість того, щоб натикатися на rate limits та будувати retry-логіку, ви резервуєте потужність. Передбачувана продуктивність, передбачувані витрати.

**Мережева латентність.** Якщо ваша інфраструктура вже на AWS (наша працює на EC2 у Франкфурті), виклики Bedrock залишаються в мережі AWS. Жодного стрибка через публічний інтернет. Нижча латентність, вища надійність.

## Висновок

Мультипровайдерні LLM-архітектури не хибні — вони передчасні для більшості команд. Ціна складності реальна: шари нормалізації, подвійна retry-логіка, непередбачувані результати, неможливий дебагінг.

Почніть з одного провайдера. Інвестуйте у вибір моделі в межах цього провайдера. Побудуйте нормальні evaluation-пайплайни. А коли будете готові до мультипровайдерності, використовуйте шар абстракції на кшталт Bedrock, який бере важку частину на себе.

Найкраща архітектура — не та, у якої найбільше провайдерів. А та, де ви можете відтворити баг з першої спроби.
